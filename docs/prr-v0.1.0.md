# Post-Release Review v0.1.0


## 1. Introduction
This document outlines the process, and results thereof, for the post-release
review for bloatware v0.1.0. The methodology used in this review is inspired by
[Shape Up](https://basecamp.com/shapeup) by Ryan Singer, Basecamp. It adapts the
core principles of shaping, boundary setting and fixed-time variable-scope
planning for project bloatware and all my hobby projects in general.

The primary objective of this review is to evaluate the design documents from
last project cycle, compare the deliverables and the actually delivered system,
identify technical debt, opportunities for enhancements, conduct research and
trade-off analysis, categorize risks and prepare a concrete pitch for the next
implementation cycle.


## 2. Methodology
The post-release review (prr) will function as a dedicated four-week track that
will take place between implementation tracks. During this four-week period, the
work is organized around four core pillars designed to move from retrospective
analysis to an actionable release pitch.

### Pillar 1: Design and Code Audit
Review original design specifications against the implemented codebase.
Identify discrepancies, incomplete requirements, software rot and accumulating
technical debt across module boundaries.

### Pillar 2: Opportunity and Research
Explore candidate feature enhancements, user feedback and architectural
improvements. Conduct technical spikes and feasibility studies to resolve
unknown risks and rabbit holes before committing to architectural deep dives.

### Pillar 3: Prioritization and Scoping
Filter candidate ideas based on fixed resource boundaries and a four-week
implementation budget. Categorize items by risk and impact, ensuring strict
definition of what remains in-scope and out-of-scope.

### Pillar 4: Pitch and Release Candidate
Package prioritized enhancements and refactoring tasks into a single pitch.
This pitch then serves as the baseline for the implementation track.
